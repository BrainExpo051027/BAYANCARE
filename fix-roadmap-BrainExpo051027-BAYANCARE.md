## 🟠 P1 — High (fix this week)

### 1. Anyone on the internet can trigger your app to send arbitrary emails
**File:** `backend/app/routes/notification_bp.py`

**Why it matters:** A stranger can use your server as a free email-sending machine, which can get your domain flagged for spam and burn through your email quota.

**How to fix it:**
Require authentication and restrict these routes to admins only, or remove them entirely outside development. Add server-side rate limiting per IP and per account, validate allowed recipient domains for test routes, and return a generic success message without exposing raw errors. Fixing this prevents email quota abuse and domain reputation damage that can stop legitimate health notifications from being delivered.

## 🟡 P2 — Medium (fix this sprint)

### 1. Raw internal error messages are returned to users during account deletion
**File:** `backend/app/routes/admin_routes.py`

**Why it matters:** When something breaks, the app tells the attacker exactly how your database is structured, which makes follow-up attacks much easier.

**How to fix it:**
Replace returned exception text with a generic message like 'Failed to delete user' and log the detailed exception only on the server. Audit other routes for the same pattern and never send str(e) or err.message back to clients. Fixing this reduces reconnaissance value for attackers and makes chained attacks harder.

### 2. Assessment deletion leaks raw backend error details to the client
**File:** `backend/app/routes/assessment_routes.py`

**Why it matters:** A failed request exposes internal database details that help attackers understand your system and plan more precise attacks.

**How to fix it:**
Return only a generic error response to the client and log the exception server-side. Remove the details field entirely from production responses and review all catch blocks for similar behavior. Fixing this cuts off schema leakage that attackers use to chain other exploits.

---

### 3. Public and unauthenticated notification endpoints return raw exception messages
**File:** `backend/app/routes/notification_bp.py`

**Why it matters:** Attackers can intentionally trigger failures and get back internal error text that reveals how your email system and backend are wired.

**How to fix it:**
Do not return str(e) to the client; replace it with a generic failure message and log the real exception privately. Combine this with authentication or route removal for these test endpoints. Fixing this reduces leakiness and makes abuse of your mail system harder.
